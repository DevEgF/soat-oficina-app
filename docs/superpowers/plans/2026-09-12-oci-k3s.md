# OCI K3s Implementation Plan

**Goal:** Install K3s and prepare a separately verifiable OCI deployment while preserving AWS.
**Architecture:** Existing ARM64 VM, single-server K3s, Neon schemas hml/prod, external secrets and New Relic.
**Spec:** ../specs/2026-09-12-oci-k3s-design.md

## Global constraints

No AWS operations or modifications to AWS deployment files. No plaintext secret
output, Git persistence or credentials passed on command lines. Keep SELinux and
firewalld. Do not claim a containerized auth service is serverless.

### 1. Bootstrap the existing VM

Files: infra-k8s repository `oci/bootstrap-k3s.sh`, `oci/namespaces.yaml`.
Input: existing SSH access. Output: Ready K3s node and hml/prod namespaces.
- [x] Pin verified K3s release, configure encryption and firewall without public 6443.
- [x] Validate script with bash -n, execute via SSH, verify node and system deployments.

### 2. Prepare application deployment

Files: `deploy/oci/chart/`, `deploy/oci/Dockerfile`, `deploy/oci/deploy.sh`.
Input: ARM64 image digest, existing secrets, environment. Output: migration then application rollout.
- [x] Separate chart with required-secret references, probes, limits and HPA.
- [x] Migration uses same image/config before rollout; production takes a digest.
- [x] Validate Helm lint/template and negative configuration cases.

### 3. Secure operator configuration

Files: `deploy/oci/configure-secrets.py`, `deploy/oci/README.md`.
Input: secrets entered directly in an interactive SSH terminal. Output: root-only
files and namespaces' Secrets, never echoed. Preserve generated identity values on rerun.
- [x] Parse Neon direct connection URL, require TLS, preserve separate environment signing keys.
- [x] Implement New Relic region/key setup through hidden input and an existing Secret.
- [x] Test parsing and rerun safety with synthetic data; configure real Secrets and verify permissions without values.

### 4. Complete external integration when configuration exists

- [x] Add and test isolated auth HTTP adapter if needed; keep Lambda untouched.
- [x] Build ARM64 images, run DB migrations, hml smoke and promote same digest to prod.
- [x] Install New Relic integration and verify received telemetry.
- [ ] Configure/verify HTTPS and OCI ingress access before external authenticated smoke.
- [x] Record actual evidence, outstanding blockers and reproduction commands.

## Checkpoint

Both ARM64 images built and imported on the VM. A native K3s Job successfully
ran Java 17.0.20 and Node 24.21.0. App and New Relic manifests passed server dry-run.
92 auth tests passed with a real local synthetic PostgreSQL timeout; existing
Lambda ZIPs built and passed offline smoke. Neon credentials and a dedicated US
New Relic ingest key are configured in root-only files and Kubernetes Secrets.
Both environments are deployed with identical image digests and successful Flyway
hooks. Real smoke validated health, staff login, database reads, customer auth in
hml and bidirectional rejection of cross-environment staff tokens.
New Relic UI queries confirmed cluster samples, logs, transactions in both
environments and hml spans. Public HTTP connection previously failed while Traefik
responded locally; HTTPS and full external business smoke remain pending.
See deploy/oci/README.md for commands and exact limits. No AWS files changed.
The new dedicated ingest key was accepted by the US Metric API (202).
