# Kotlin Application on EKS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `$subagent-driven-development` (recommended) or `$executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Adaptar a aplicação Kotlin/Spring existente para autenticação de cliente, RDS compartilhado, logs/métricas correlacionados e deploy Helm automático no EKS.

**Architecture:** O domínio continua hexagonal. O JWT identifica o cliente por UUID; controllers nunca recebem CPF depois da emissão do token. Um Helm chart implanta o mesmo digest em namespaces hml/prod, executa Flyway em Job antes do rollout, monta Secrets Manager por CSI e expõe NodePorts fixos ao NLB.

**Tech Stack:** Java 17, Kotlin 2.4.10, Spring Boot 4.1.1, Spring Security Resource Server, PostgreSQL 16, Flyway, Gradle, Helm 3, Kubernetes/EKS 1.35, ADOT, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-08-31-fase-3-aws-design.md`

## Global Constraints

- Preservar a cobertura JaCoCo de pelo menos 80% nos packages domain/application.
- JWT: HS256 derivado por SHA-256, `iss=oficina`, `aud=oficina-api`, claim `env`, scope por lista.
- Rotas de cliente usam `/api/customer/**`; `/api/public/os/**` deixa de existir.
- Hml/prod usam schemas Flyway separados e somente migrations aditivas.
- Deployment normal usa `SPRING_FLYWAY_ENABLED=false`; o Job de migration usa `true`.
- Service hml usa NodePort 30080; prod usa 30081.
- HPA: mínimo 1, máximo 3, CPU 70%, memória 80%.
- Logs são JSON e nunca contêm CPF, JWT, senha ou connection string.
- Imagem ECR é implantada por digest/tag SHA, nunca `latest`.
- O frontend recebe somente ajustes funcionais mínimos; não há redesenho.
